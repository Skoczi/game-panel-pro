# Audyt API v1 — 27.09.2026

Audyt kodu, kontraktu OpenAPI i istniejących testów HTTP. Punkt odniesienia: commit `180d62c`. Bez instalacji serwerów, zmian kont i wywołań mutujących na produkcji. Poniższe nowe endpointy i pola są propozycją, nie opisem wdrożonych funkcji.

## Ocena

API v1 nadaje się dziś do ograniczonego monitoringu, start/stop/restart i tworzenia backupów. Nie jest jeszcze API do automatycznego zakładania i obsługi usług hostingowych. Fundament autoryzacji i deduplikacji operacji warto zachować; rozszerzać publiczny kontrakt nad istniejącymi usługami panelu i agentów.

## Co jest zaimplementowane

| Metoda | Ścieżka względem `/api/v1` | Zakres |
|---|---|---|
| GET | `/servers` | Serwery przypisane do tokenu; limit 1–100, kursor |
| GET | `/servers/{uuid}` | Ten sam krótki rekord co na liście |
| GET | `/servers/{uuid}/resources` | CPU, RAM, dysk, limity CPU/RAM, czas próbki |
| GET | `/servers/{uuid}/backups` | Nazwa, rodzaj, rozmiar, data modyfikacji |
| POST | `/servers/{uuid}/backups` | Backup Native z trwałym kluczem idempotencji |
| POST | `/servers/{uuid}/power` | Start/stop/restart z trwałym kluczem idempotencji |
| GET | `/operations/{id}` | Odczyt operacji dostępnej właścicielowi |

Obecny rekord serwera: `id`, `number`, `name`, `provider`, `status`, `observedAt`. `id` to UUID floty, `number` to globalny numer, np. 101. Ścieżki v1 nadal wyszukują po UUID, mimo że wewnętrzne `/api/fleet/{id}/context` akceptuje również numer.

Token: sześć zakresów (`servers.read`, `resources.read`, `backups.read`, `backups.create`, `operations.read`, `servers.power`), lista 1–100 istniejących UUID, ważność maksymalnie rok. Uprawnienia konta i przypisanie do serwera są sprawdzane ponownie przy żądaniu. Sekret jest zwracany jednorazowo; baza przechowuje hash. Token nie daje automatycznie dostępu do przyszłych serwerów.

## Ustalenia i priorytety

| Priorytet | Ustalenie | Skutek / zalecenie |
|---|---|---|
| P1 | `serverDto` zwraca surowy zapisany `status`. Nie sprawdza dostępności node jak wewnętrzna lista floty. | Integracja może traktować stare `running` jako bieżący stan. Dodać `availability`, `stale`, czasy obserwacji i rozróżnić nieznany stan od zatrzymania. |
| P1 | Detail to ten sam DTO co lista. | Brak danych do karty usługi: adresów gry/TV, gry, template, graczy, mapy, uptime, uprawnień i możliwości. Wprowadzić osobny kontrakt szczegółów. |
| P1 | Token wymaga istniejących serwerów; brak scope instalacji i polityki zasobów. | Nie wystarczy dopisać `POST /servers`. Potrzebny ograniczony token provisioningowy i atomowe nadanie dostępu do utworzonej usługi. |
| P1 | Dziennik operacji wymaga serwera i runtime już przy przyjęciu. Obsługuje backup/power. | Instalacja musi przeżyć stan przed utworzeniem kontenera, restart panelu i niepewną odpowiedź agenta. Rozszerzyć model operacji i rezerwacji. |
| P2 | Brak filtrowania/sortowania po adresie, nazwie, grze i node. Lista sortuje po UUID. | Rozbudować zapytania i stabilny kursor. Publiczne domyślne sortowanie zmieniać ostrożnie, aby nie zepsuć istniejących klientów. |
| P2 | Wspólny handler listy i detail przetwarza `after` również dla detail. | Parametr kursora może wykluczyć wskazany rekord i dać 404. Oddzielić walidację listy od szczegółów. |
| P2 | Lista pobiera całą flotę i sekwencyjnie sprawdza uprawnienia kandydatów. | Przy rozbudowie użyć zapytania uwzględniającego token i granty, stronicować przed wzbogacaniem danych. Nie odpytuj każdego agenta osobno dla każdego wiersza. |
| P2 | Operacje nie mają jednolitego procentu, etapu, wyniku, błędu ani endpointu listy. Power completion oznacza zakończenie komendy, nie gotowość gry. | Rozdzielić wynik operacji od health gry; ujednolicić statusy i diagnostykę. |
| P2 | Jeden globalny odbiorca podpisanych webhooków w obecnym store. | Dla wielu integracji potrzebne subskrypcje z filtrami zdarzeń/serwerów i odrębnymi sekretami. |

Nie stwierdzono braku autoryzacji na podstawie przejrzanych handlerów. Nie jest to pełny pentest. Endpointy członkostwa floty są za `rootOnly`; nie należy kopiować samych handlerów do API v1 bez tej warstwy.

## Etap 1: lista i szczegóły serwerów

Zachować UUID jako kanoniczne `id`; dodać wygodny alias globalnego numeru, np. `/servers/101`, prowadzący przez dokładnie te same kontrole dostępu. Numer nie jest lokalnym ID na node i nie może być ponownie wykorzystany.

Proponowane pola listy:

- Tożsamość: `id`, `number`, `displayId`, `name`, `game.id`, `game.name`, `template.id`, `template.version`.
- Połączenie: `connection.host`, `connection.gamePort`, `connection.tvPort`, `connection.tvEnabled`, `connection.joinUrl` tam, gdzie gra go obsługuje. RCON nie dostaje sztucznie osobnego portu, jeżeli używa portu gry.
- Lokalizacja: publiczna nazwa node i lokalizacja. Hostowe IP, ścieżki oraz adres API agenta pozostają poza standardowym DTO.
- Stan: `status`, `availability`, `observedAt`, `stale`; osobno `gameResponse.state`, `players.current`, `players.max`, `map`, `latencyMs`, czas obserwacji.
- Linki: `links.panel`, `links.console`, `links.files`.

Detail dodatkowo: przyznane zasoby, uptime, jawny zestaw `capabilities`, dozwolone akcje wynikające z przecięcia uprawnień konta i tokenu, podsumowanie backupów, stan instalacji, aktywna operacja. Szczegóły instalacji dodatków dostępne przez osobny podzasób.

Proponowane zapytania:

```http
GET /api/v1/servers?limit=50&sort=connection&include=gameResponse,resources
GET /api/v1/servers?filter[game]=cs16&filter[status]=running&search=DD2
GET /api/v1/servers/101
```

`include=resources` wymaga `resources.read`; nie wolno obejść zakresu przez rozszerzenie listy. Sort adresu liczbowy (IPv4/IPv6 i port), z UUID jako rozstrzygnięciem remisów. Nowy kursor musi uwzględniać sortowanie i filtry. Brak danych oznacza `null` lub jawny stan niedostępności, nigdy fikcyjne zero. Jedna awaria node nie może psuć całej listy. Czasy próbek należy podawać osobno dla zasobów i zapytania gry.

## Etap 2: instalacja przez API

Proponowany przepływ:

1. `GET /templates` — opublikowane, dostępne dla tokenu wersje i schemat dozwolonych zmiennych; bez sekretów i hostowych instrukcji.
2. `GET /nodes` oraz `GET /nodes/{id}/allocations` — tylko dozwolone miejsca instalacji i alokacje.
3. `POST /server-plans` — walidacja template/version/hash, zasobów, IP, portu gry/TV, mountów i dostępności lokalnego pakietu gry. Plan ma termin ważności. Sam preview nie gwarantuje rezerwacji.
4. `POST /servers` z `planId` i `Idempotency-Key` — ponowna walidacja, atomowa rezerwacja numeru i alokacji, zapis trwałej operacji; odpowiedź `202` i `Location`.
5. `GET /operations/{id}` — etap, rzeczywisty postęp, wynik oraz link do serwera. Ukończona instalacja domyślnie zostawia serwer zatrzymany (`startAfterInstall: false`).

Przykładowy plan — nowy kontrakt, jeszcze nie działa:

```json
{
  "name": "DD2 #2",
  "template": { "id": "<template-id>", "version": 1 },
  "nodeId": "<allowed-node-id>",
  "allocationId": "<allowed-allocation-id>",
  "resources": { "cpuCores": 1, "memoryBytes": 1073741824 },
  "startAfterInstall": false
}
```

Token provisioningowy: `servers.create`, odczyt katalogu oraz operacji; jawne limity liczby serwerów, CPU/RAM/dysku, dozwolone node/template/alokacje. Nie przekazywać publicznie dowolnych komend, obrazów, host paths ani surowych mountów. Dla Classic Offensive plan sprawdza dostępność lokalnego pakietu i wersji współdzielonych plików.

Nowy serwer musi od razu trafić do jawnie określonego zakresu integracji — atomowy grant tylko do tej usługi, bez rozszerzania istniejących tokenów na całą przyszłą flotę. `externalId` pomaga łączyć serwer z zamówieniem, lecz nie zastępuje idempotencji. Powtórka po utracie odpowiedzi nie tworzy drugiego serwera. Niepewny wynik nie zwalnia automatycznie portu, który mógł już zostać użyty.

Wykorzystać istniejące templates, podpisane bilety, walidację portów, centralną rezerwację numerów i instalator. Wydzielić wspólne usługi z handlerów; nie implementować drugiego instalatora ani przekazywać tokenu klienta do agenta.

## Etap 3: użytkownicy, dostęp do serwera i admini gry

| Obszar | Proponowane endpointy | Zasada |
|---|---|---|
| Konto panelu | `GET/POST /users`, `GET/PATCH /users/{id}` | Osobne zakresy. Konto operatora i właściciel wymagają dodatkowych reguł; chronionego właściciela nie można zmieniać zwykłym tokenem. |
| Dostęp do usługi | `GET /servers/{id}/members`, `PUT/DELETE /servers/{id}/members/{userId}` | Presety i jawne uprawnienia. Brak możliwości nadania praw większych niż dopuszcza właściciel tokenu i polityka delegowania. |
| Administrator w grze | `GET/POST /servers/{id}/game-admins`, `PATCH/DELETE /servers/{id}/game-admins/{adminId}` | SteamID, uprawnienia, provider, opcjonalna ważność. Nie mylić z kontem panelu. |

Preset `server-admin`: pliki, konfiguracja gry, konsola gry i dozwolone backupy. Bez terminala systemowego, zmiany CPU/RAM, IP/portów, node i mountów. Warto dodać także `viewer` i `console-operator`. Oddzielić możliwość nadawania dostępu innym osobom od zwykłego administrowania serwerem.

Admini gry wymagają adapterów: AMXX, SourceMod oraz konkretnych systemów uprawnień pluginów CS2. Sam CounterStrikeSharp nie gwarantuje jednego uniwersalnego formatu adminów. Obecny edytor ReHLDS obsługuje SteamID bez hasła i zapis całego tekstu; nowy CRUD powinien zachowywać komentarze/nieobsługiwane wpisy, używać wersji pliku/If-Match i tworzyć snapshot. Zapis i zastosowanie praw w działającej grze to dwa różne wyniki. Data wygaśnięcia wymaga trwałego procesu usuwania praw, nie tylko pola w odpowiedzi.

## Etap 4: pełna obsługa usługi

- `GET /servers/{id}/activity`, `GET /operations` — filtry rodzaju/stanu/serwera, stronicowanie; audyt zawiera konto, identyfikator tokenu, requestId, operationId i wynik, bez sekretów.
- `/servers/{id}/addons` — katalog, wykryte wersje, instalacja/usuwanie, zależności, backup i rzeczywisty postęp. Wymagany capability danej gry.
- `/servers/{id}/maps`, `/rotation`, `/config` — strukturalne operacje z kontrolą wersji i zachowaniem ręcznych zmian.
- Backupy: restore, pobranie, usunięcie i retencja, każde z osobnym zakresem. Restore jako długa operacja z kontrolą stanu serwera.
- SFTP: odczyt statusu, enable/disable, rotacja hasła; sekret jednorazowo po utworzeniu/rotacji, nigdy w liście serwerów.
- Harmonogramy, komendy konsoli i strumień zdarzeń — oddzielne uprawnienia. Terminal hosta nie jest potrzebny standardowej integracji.
- Klonowanie, reinstalacja i usunięcie — etap późniejszy, z trwałym dziennikiem, kontrolą równoległych operacji i precyzyjną polityką odtwarzania.
- Webhooki: `server.created`, `install.progress/completed/failed`, `power.completed`, `backup.completed/failed`, `member.changed`, `game-admin.changed`; filtry per integracja, HMAC, retry, deduplikacja po eventId, obsługa zdarzeń poza kolejnością.

## Kolejność wdrożenia i odbiór

1. Kontrakt DTO list/detail, świeżość, globalny alias numeru, capability i filtry.
2. Polityki tokenów provisioningowych + trwałe operacje + instalacja.
3. Konta i członkostwa serwerów; następnie adapter AMXX adminów gry.
4. Dodatki, backup restore, harmonogramy i subskrypcje zdarzeń.

Na każdym etapie aktualizacja OpenAPI i przykładów curl. Zachować obecne pola/UUID i istniejące tokeny. Nowe pola są addytywne; domyślną zmianę sortowania i schematu kursorów traktować jako świadomą zmianę kompatybilności.

Testy odbiorowe: odcięcie dostępu po odebraniu grantu/dezaktywacji konta; niedostępny node bez fałszywego statusu; izolacja danych między tokenami; brak sekretów w odpowiedziach; równoległa rezerwacja tego samego portu; powtórzenie instalacji po timeout/restart; brak automatycznego startu gry; konflikt edycji adminów; brak eskalacji do operatora/właściciela; zgodność rzeczywistych odpowiedzi z OpenAPI.
